# 投餵週期時序圖：如何取得實測資料並完成分析

使用者所指的原 **Figure 6**，在移除 Figure 5 狀態機圖後，已自動編為 **Figure 5**，LaTeX 標籤仍是 `fig:timing`。

目前的 `figures/6p/timing.pdf` 是由 `generate_figures.py` 的 `timing()` 畫出的**符號示意圖**：線條形狀與區段寬度沒有來自實驗量測。專案目前也沒有對應的影片、逐影格偵測紀錄或投餵事件紀錄。以下是把它換成可重建實測圖的完整流程；不會把示意曲線當成實驗結果。

## 1. 最後要畫的是什麼

同一個投餵週期需要三種資訊，共用一條時間軸：

| 圖中內容 | 實際資料來源 | 代表的意思 |
| --- | --- | --- |
| 上方投餵訊號 | Pi 送出的投餵命令／停止命令；若有回授則另記錄實際動作 | 命令何時發出、持續多久。沒有動作感測器時，圖例應寫 `Commanded actuator activity`。 |
| 原始曲線 `A_t` | 相機影格經 RF-DETR 得到的飼料框 | 固定 ROI 內的「可見飼料框面積代理量」，單位 px²。 |
| 濾波曲線 `Â_t` | 對 `A_t` 進行因果 Kalman 濾波 | 減少反光、遮擋與漏檢造成的短時間波動。 |
| Feed / Wait / Observe / Decide 區間 | 控制流程的狀態轉換紀錄 | 哪段時間正在送出投餵動作、等待落料、觀察或決策。 |
| 起終點及 `ρ` | 同一觀察視窗的第一筆和最後一筆有效濾波值 | 可見飼料在這個視窗中的相對消失比例。 |

上方的一個高電位區間通常是「投餵動作命令有效期間」，不是伺服馬達每一個 PWM 脈衝。若要畫實際 PWM 電壓波形，需另外用邏輯分析儀或示波器量測，並對齊時間；目前的時序圖不需要這種電氣量測。

## 2. 先固定實驗條件與參數

固定相機位置、解析度與 ROI，鎖定要使用的模型版本、飼料類別 ID、信心閾值 `τ`，以及每次的投餵命令。影片中必須看得到飼料進入水面後的變化。

另外保存這些設定：

- `session_id`、`cycle_id`、模型版本與設定檔版本。
- 影像解析度、ROI 座標、框座標所使用的解析度。
- 分析取樣頻率 `f_s`、觀察樣本數 `L`、等待時間。
- Kalman 的 `Q`、`R`、初始狀態設定及品質閘門閾值。
- 致動器命令 `u_k`，以及獨立秤重校正得到的投餵量 `g(u_k)`；尚未校正時不要把命令值換算成克數。

相機串流 FPS 與分析取樣頻率是兩件事。相機可以持續錄影，而後端只在預先定義的時間點分析影格。取樣頻率要能符合部署實際處理能力；不要用後端偶爾回傳的速度冒充固定頻率。

**取樣定義已統一：** `L` 表示觀察視窗內的樣本數，而不是樣本間隔數。第一個索引是 0，最後一個是 `L-1`，因此：

\[
T_{\mathrm{obs}}=(L-1)/f_s.
\]

例如「2 Hz、21 筆」對應 10 秒觀察時間；這是配置範例，不是本專案已量測或已選定的參數。原本以 `t-L` 表示起點會包含 `L+1` 筆，正文與示意圖已改成 `t-L+1`。

## 3. 同時記錄事件、影格與偵測結果

依論文參考架構，Pi 負責擷取／串流與轉送致動命令；後端伺服器執行 RF-DETR、品質檢查、Kalman 與 Feed／Wait／Observe／Decide 狀態機；BMduino 控制伺服馬達。這是與架構圖及正文一致的設計配置，尚未由部署追蹤紀錄驗證。Pi 的本地命令逾時保護也需要實測，以確保伺服器斷線時不再續餵。

以下是待實作／驗證的記錄規格：Pi 保存影格與擷取時間，後端保存偵測、品質、估計與決策結果，BMduino 的回覆則區分命令接收與動作完成。所有訊息都必須攜帶同一組 `session_id / cycle_id / frame_id`，才能事後合併。下列 CSV 欄位不代表現有部署已產生這些紀錄。

建議至少保存下面三份檔案，另外保存原始影片或可回查的影格。

### A. `events.csv`：投餵與狀態事件

```csv
session_id,cycle_id,event,timestamp_pi_ns,source,command_id,value,time_basis
```

`event` 至少涵蓋：投餵命令發出、命令回覆、動作完成回覆、進入 Wait、進入 Observe、離開 Observe、收到決策，以及任何故障／Suspend。

`time_basis` 要區分「Pi 發出命令」「Pi 收到回覆」「已同步的實際動作時間」。收到 acknowledgement 只證明命令被回覆，不能直接當成馬達已開始運動。若只有接收端時間，圖說就應反映這個量測範圍。

### B. `frames.csv`：每個預定取樣位置一列

```csv
session_id,cycle_id,slot_index,slot_pi_ns,frame_id,capture_pi_ns,result_received_pi_ns,state_at_capture,quality_ok,quality_reason,feed_count,mean_feed_conf,raw_area_px2,kalman_area_px2,prediction_only
```

- `slot_index`：0 到 `L-1`；即使影格遺失，也保留這個位置。
- `capture_pi_ns`：影像實際擷取時間；沒有取得影格時留空。
- `result_received_pi_ns`：Pi 收到該影格結果的時間，可用來分析端到端回傳延遲。
- `quality_reason`：例如 glare、occlusion、blur、missing frame、timeout，原因可複選。
- `raw_area_px2`：對有效影格計算的代理量。沒有結果／品質不合格時不能填成 0。
- `prediction_only`：這一筆是否只做 Kalman 預測，沒有用觀測值更新。

### C. `detections.csv`：每個偵測框一列

```csv
session_id,cycle_id,frame_id,class_id,confidence,x1,y1,x2,y2
```

框座標要還原到同一個固定解析度。若模型輸入有縮放或 letterbox，先還原，再計算框面積與 ROI 交集。

## 4. 時間對齊要用擷取時間

建議以 Pi 的單調時鐘作為此圖的共同時間基準。橫軸使用：

\[
s_j=(T^{\mathrm{capture}}_j-T^{\mathrm{feed\ command}}_k)/10^9.
\]

單位為秒。從影格擷取到推論完成會經過網路與處理延遲，因此不要用「後端收到影像時間」或「偵測結果到達時間」替代影格擷取時間。

後端應把 `frame_id` 與擷取時間原樣帶回。不同裝置的 monotonic timestamp 沒有共同起點，不能把 Pi、伺服器與微控制器的數字直接相減。跨裝置事件若要放在同一條時間軸，必須先做時鐘對應並記錄誤差，或明確使用 Pi 送出／收到訊息的時間。伺服器內部推論耗時則可用該伺服器自己的起終時間相減。

同一個觀察視窗內，依取樣位置處理資料。對回傳亂序、重複 frame ID、遲到影格及逾時，需事先訂定取樣容許誤差與截止規則，不能依曲線是否好看才決定是否保留。沒有影格的取樣點用預定取樣時間標記缺失，不能假造擷取時間。

## 5. 從偵測框計算原始 `A_t`

對影格 j 的每個框，令 `w = x2-x1`、`h = y2-y1`。依正文目前定義，只保留飼料類別、信心值不低於 `τ`、且與固定 ROI 至少有交集的框：

\[
A_j=\sum_i w_i h_i\,\mathbb{I}(y_i=\mathrm{feed})\,
\mathbb{I}(c_i\ge\tau)\,\mathbb{I}(B_i\cap\Omega\ne\varnothing).
\]

目前公式加總的是**整個符合條件的框面積**。若另改為「框在 ROI 內的裁切面積」或「框的聯集面積」，那是不同的代理量，必須同步修改方法定義，不能混著比較。

特別區分下列三種情況：

| 情況 | 原始數值如何記錄 | 濾波如何處理 |
| --- | --- | --- |
| 品質合格、偵測完成、沒有飼料框 | `A_j = 0` | 可以用 0 更新。 |
| 品質不合格 | `A_j` 留空／NaN；原始框另存 | 只做預測。 |
| 網路逾時或遺失影格 | `A_j` 留空／NaN，保留取樣位置 | 只做預測。 |

「沒有飼料框」不等於「平均飼料信心為零」。此時平均信心應標為不可用，並使用其他影像品質指標判定影格是否合格；否則真正吃完的影格可能全被誤判成無效。

框重疊、飼料沉底、漂出 ROI 或被魚遮住，都可能讓 `A_j` 與實際飼料量不同。因此這條曲線不是飼料重量，也不是精確顆粒數。

## 6. 逐點做因果 Kalman 濾波

為了容易重建單次觀察窗，可採用以下明確的初始化方式：第一筆有效原始值作為 `x̂_0`，初始不確定度 `P_0` 另行記錄。`Q / R / P_0` 用校正資料選定後固定；如果實際部署採跨週期持續濾波，也需保存上一週期的狀態與相同的初始化規則。

在固定的分析取樣位置，每次先預測：

\[
\hat x^-_j=\hat x_{j-1},\quad P^-_j=P_{j-1}+Q.
\]

若影格有效，再更新：

\[
K_j=\frac{P^-_j}{P^-_j+R},\qquad
\hat x_j=\hat x^-_j+K_j(A_j-\hat x^-_j),\qquad
P_j=(1-K_j)P^-_j.
\]

否則保留預測值與預測不確定度，並標記 `prediction_only=1`。繪圖使用 `Â_j = max(0, x̂_j)`，同時保存未截斷的狀態以利檢查。

因為 `A` 的單位是 px²，`Q / R / P` 是面積訊號的變異量，單位是 px⁴；更換解析度會改變這些量的尺度。固定每一步的 `Q` 也預設固定取樣時間，因此遺失位置不能直接刪掉而少算一次預測。

校正時可在獨立場次，以人工檢查的同定義參考訊號比較參數組合，兼顧誤差與反應延遲。人工像素遮罩面積與偵測框加總面積不是相同量，若兩者比較，需要另外說明框面積本身的偏差。不要用同一測試週期反覆調 `Q / R`，直到得到預期的下降曲線；也不要用需要未來資料的雙向平滑替代部署用的因果結果。

## 7. 取得端點與 `ρ`

先透過校正影片確認落料與水面穩定所需時間，將這段時間列為 Wait，才開始 Observe。不要直接用馬達運轉或飼料尚在落下時的面積當成視窗起點。

對一個有 L 個取樣位置的視窗，使用第一筆和最後一筆**實際有效觀測所對應的濾波值**：

\[
\rho=\frac{\hat A_0-\hat A_{L-1}}{\max(\hat A_0,\varepsilon)}.
\]

`ε` 及「初始可見飼料太少」的判定門檻都需在校正資料上設定。數學上加 `ε` 只是避免除以零，不能讓幾乎沒有可見飼料的週期變成可靠的高需求判定。

首末位置無效、有效樣本太少或出現裝置故障時，該週期應標記不可用並暫停自動續餵；不要把中間兩個好看的點任意替換成首末點，因為那會改變觀察長度。起點太低則不能觸發增加。若只為離線研究另算不同長度的有效片段，需另外報告時間範圍，不能與固定視窗的決策混用。

**純計算範例：** 若第一筆 `Â=10000 px²`、最後一筆 `Â=2000 px²`，且分母使用 10000，則 `ρ=0.8`，表示該視窗的可見代理量減少 80%。這不代表魚吃掉 80% 的飼料；上述數字也不是本專案量測結果。如果訊號反而增加，`ρ` 可以為負，不要為了圖面好看把負值裁成零。

## 8. 真正繪圖與檢查的步驟

1. 選定一個完整的 `cycle_id`，保存其原始影片及全部事件，不只保留成功餵食的片段。
2. 合併時間與 frame ID；把 Feed、Wait、Observe、Decide 的實際邏輯事件放到共同時間軸。
3. 按相同設定重新計算 `A_j`，驗證它與線上紀錄一致，再依序執行 Kalman，不能使用後面資料回填前面估計。
4. 用同一個秒數橫軸畫三個對齊面板：上方為命令有效區間，中間為原始與濾波面積，下方為狀態區段；也可把狀態區段以背景色疊在中間面板。
5. 原始面積用灰線，濾波面積用另一種顏色與線型。無效原始值要斷線；只預測的濾波區段用虛線或特殊符號。不要畫出跨遺失資料、看似實際量測的實線。
6. 標出 `Â_0`、`Â_(L-1)`、觀察長度、有效樣本數及 `ρ`。不可用週期要直接寫 `invalid / suspended`，不顯示可用的投餵建議。
7. 決策事件必須在需要的觀測與處理完成之後，不能因為把影格對齊到擷取時間，就把真正的命令發出時間也提早。另報告觀察結束至決策／動作的延遲。
8. 匯出向量 PDF，保留 `events.csv / frames.csv / detections.csv`、參數設定與程式版本，使別人可重建完全相同的圖。

論文要換成實測圖時，將新輸出檔放入例如 `assets/feeding_cycle_measured.pdf`，把 `fig:timing` 的 `includegraphics` 換成該檔，並把圖說改為實際場次、取樣頻率、視窗長度、參數與缺失資料標記。未取得資料以前，繼續保留 `schematic` 標示。

## 9. 這張圖能支持什麼分析

一張完整週期圖可以檢查命令、等待、觀察和決策順序，觀察濾波是否減少短時間抖動，以及決策是否使用了正確端點。要聲稱改善準確度、節省飼料或提升 FCR，還需要獨立參考標註、重複週期、對照組與對應實驗。

若要報告濾波效果，應在有參考的保留資料上比較原始與濾波誤差及反應延遲。`A_t` 在餵食後本來就可能持續下降，因此不能只把整段曲線的變異數變小當作正確性改善；應在穩定參考區段或去除真實趨勢後比較殘差波動。
