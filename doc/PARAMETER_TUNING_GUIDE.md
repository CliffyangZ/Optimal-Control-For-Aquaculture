# YOLOv26 训练参数详解与调优指南

## 参数速查表

| 参数 | 当前值 | 含义 | 调优范围 | 对性能的影响 |
|------|--------|------|---------|-----------|
| `weights` | yolo26s.pt | 预训练权重 | yolo26n/s | 重大 |
| `variant` | yolo26s | 模型大小 | n/s/m/l | 重大 |
| `epochs` | 300 | 训练轮数 | 100-500 | 中等 |
| `batch` | 16 | 批量大小 | 4-64 | 高 |
| `imgsz` | 832 | 输入图像大小 | 416-1024 | 中等 |
| `workers` | 4 | 数据加载线程 | 0-16 | 低 |
| `mosaic` | 1.0 | 马赛克增强概率 | 0.0-1.0 | 中等 |
| `close_mosaic` | 10 | 关闭马赛克的轮数 | 0-50 | 低 |
| `mixup` | 0.2 | 混合增强概率 | 0.0-1.0 | 中等 |
| `patience` | 50 | 早停耐心值 | 10-100 | 低 |
| `seed` | 42 | 随机种子 | 任意 | 无 |

---

## 详细参数解析

### 1. weights: yolo26s.pt
**功能**：指定预训练权重文件路径

**原理**：
```
预训练权重 = 用大规模通用数据集（COCO等）预先训练的模型参数
│
├─ 迁移学习：复用已学的特征
├─ 快速收敛：不从零开始训练
└─ 更高精度：用通用知识初始化
```

**调优指南**：
```python
# ✅ 推荐：使用预训练权重 (第一次训练)
weights: yolo26s.pt

# ⚠️ 有时尝试：从另一个模型的权重开始
weights: yolo26n.pt  # 如果要轻量化
weights: /path/to/custom_pretrained.pt  # 自定义预训练

# ❌ 不推荐：从零开始 (除非数据量巨大)
weights: yolo26s.yaml  # 只用架构，参数随机初始化
```

**对性能的影响**：
- 预训练权重 vs 随机初始化：**+10-15% mAP**
- 不同预训练来源：**±2-3% mAP**

---

### 2. variant: yolo26s
**功能**：指定模型的大小变体

**模型比较**：
```
┌─────────────────────────────────────────────────┐
│ YOLOv26 模型变体对比                             │
├──────────┬───────┬──────────┬────────┬──────────┤
│ 变体      │ 参数  │ 相对大小 │ 推理ms │ mAP提升  │
├──────────┼───────┼──────────┼────────┼──────────┤
│ nano (n) │ 3.2M  │ 0.3x     │ 3ms    │ baseline │
│ small(s) │ 11M   │ 1.0x     │ 5ms    │ +3-4%    │
│ medium(m)│ 25M   │ 2.3x     │ 8ms    │ +5-6%    │
│ large(l) │ 43M   │ 4.0x     │ 15ms   │ +6-7%    │
│ xlarge(x)│ 68M   │ 6.3x     │ 25ms   │ +7-8%    │
└──────────┴───────┴──────────┴────────┴──────────┘

注：yolo26 可能没有官方的m/l预训练权重
```

**调优原理**：
```
模型大小 ↑  →  特征提取能力 ↑  →  精度 ↑
             但推理速度 ↓，内存占用 ↑
```

**调优建议**：
```yaml
# 🎯 平衡精度和速度 (推荐)
variant: yolo26s  # 当前配置

# 🚀 优先精度 (如果显存足够)
variant: yolo26m  # 需要下载或自己训练

# ⚡ 优先速度 (移动设备/边缘计算)
variant: yolo26n  # 3倍快，但精度低3-4%

# 🎖️ 最高精度 (服务器端)
variant: yolo26l  # 但yolo26没有官方权重
```

**显存需求**（imgsz=640, batch=16）：
```
yolo26n: ~2GB
yolo26s: ~4GB  ← 当前配置
yolo26m: ~8GB
yolo26l: ~12GB
```

### 3. epochs: 300
**功能**：训练轮数（对整个数据集的完整遍历次数）

**原理**：
```
Epoch 1:   模型学习基本特征
   ↓
Epoch 50:  精调中层特征，开始过拟合
   ↓
Epoch 150: 模型已充分学习，精度接近收敛
   ↓
Epoch 300: 继续训练，精度增长变缓
   ↓
Epoch 500+: 过度训练，可能开始过拟合
```

**损失曲线通常长这样**：
```
Loss
  │     ╱╲
  │    ╱  ╲
  │   ╱    ╲___
  │  ╱         ╲___
  │ ╱              ╲___
  │╱                   ╲───
  └────────────────────────── Epoch
  0  50  100  150  200  250  300
```

**调优指南**：
```yaml
# ✅ 推荐：300 epochs（当前配置）
epochs: 300  # 对大多数场景足够

# 早期实验：快速测试超参数
epochs: 50   # 1小时训练，快速反馈
# 缺点：模型未充分训练

# 高精度要求：更多epoch
epochs: 500  # 需要2倍时间

# 配合 patience 使用（早停）
patience: 50  # 50个epoch无改进就停止
# 实际可能在 epoch 250 左右停止
```

**最优epoch判断**：
```
观察指标：
1. 验证mAP是否继续上升？
   是 → 继续增加epoch
   否 → 可以停止

2. 训练loss和验证loss是否在靠近？
   靠近 → 模型已充分学习

3. WandB监控图表
   mAP曲线变平缓 → 已接近收敛
```

### 4. batch: 16
**功能**：每次梯度更新前处理的样本数量

**原理**：
```
Batch太小 (2-4)           Batch适中 (16)          Batch太大 (256)
├─ 梯度估计噪声大          ├─ 梯度稳定            ├─ 梯度平滑
├─ 收敛不稳定             ├─ 收敛快速            ├─ 容易陷入局部最优
├─ 需要更多epoch          ├─ 利用GPU高效         ├─ 需要降低学习率
├─ 推理速度快             ├─ 平衡性好            ├─ 推理延时长
└─ 内存占用少             └─ 推荐 ✅             └─ 内存占用多
```

**数学原理**：
```
梯度 = 平均损失梯度(batch内所有样本)

Batch大小 ↑
  ├─ 梯度估计更准确（更多样本平均）
  ├─ 但每个epoch包含的梯度更新次数 ↓
  └─ 需要更多epoch来补偿

例如：
Dataset = 5000张图
batch=8   → 625 次梯度更新/epoch
batch=16  → 312 次梯度更新/epoch
batch=32  → 156 次梯度更新/epoch

所以 batch ↑ 需要 epochs ↑
```

**调优指南**：
```yaml
# 根据显存调整
# GPU显存 < 4GB
batch: 8

# GPU显存 4-8GB (推荐当前配置)
batch: 16   ✅ 稳定和效率的平衡

# GPU显存 8-16GB
batch: 32   # 更稳定的梯度，但需要更多epoch

# GPU显存 > 16GB
batch: 64   # 梯度最稳定，但epoch需要翻倍
```

**batch调整的连锁反应**：
```yaml
# 从 batch: 8 升级到 batch: 16
model:
  batch: 16          # ← 改这个
  epochs: 300 → 350  # ← 需要增加epoch补偿
  lr0: 0.01          # ← 学习率可能需要调整
```

**显存计算**：
```
显存占用 ≈ batch * image_size² * 模型大小

例如：batch=16, imgsz=832, yolo26s
显存 ≈ 16 × 832² × 20M ≈ 4-5GB
```

### 5. imgsz: 832
**功能**：输入图像大小（长宽都调整到这个尺寸）

**原理**：
```
小图像 (416)          中等图像 (640)        大图像 (832)         巨大 (1024)
├─ 丢失细节           ├─ 平衡的选择         ├─ 保留丰富细节       ├─ 极高的细节
├─ 小目标检测差       ├─ 中小目标可以       ├─ 小目标检测好       ├─ 小目标完美
├─ 推理快 (3ms)       ├─ 推理中 (5ms)       ├─ 推理慢 (8ms)       ├─ 推理很慢 (15ms)
├─ 显存少             ├─ 显存中             ├─ 显存多             ├─ 显存非常多
└─ 精度 baseline      └─ 精度 +2-3%         └─ 精度 +3-4%          └─ 精度 +4-5%
```

**图像大小的平方关系**：
```
显存占用 ∝ image_size²

640 → 832 的变化：
832² / 640² = 1.69倍
显存增加约70%

例如：
imgsz=640, batch=16  → 4GB显存
imgsz=832, batch=16  → ~6-7GB显存
imgsz=1024, batch=16 → ~10GB显存
```

**对象检测中的影响**：
```
你的任务：检测鱼和饲料（都是相对小的目标）

小目标在不同分辨率下的像素数量：
Fish (实际宽度~10cm, 距离2米)
  ├─ 416x416: ~5×5像素      ← 太小，难以检测
  ├─ 640x640: ~12×12像素    ← 可检测，但细节少
  ├─ 832x832: ~15×15像素    ← 较好，细节充分
  └─ 1024x1024: ~20×20像素  ← 更好，但显存压力大

Feed (实际宽度~2cm)
  ├─ 416x416: ~1×1像素      ← 几乎不可见
  ├─ 640x640: ~2×2像素      ← 勉强可检测
  ├─ 832x832: ~3×3像素      ← 较好
  └─ 1024x1024: ~4×4像素    ← 更清晰
```

**调优建议**：
```yaml
# 对于小目标检测（你的场景）
# ✅ 推荐：832 (当前配置最优)
imgsz: 832

# 权衡选项
imgsz: 640   # 传统选择，显存少20%
imgsz: 704   # 折中方案
imgsz: 1024  # 如果有足够显存，精度 +1-2%

# 注意：必须是32的倍数
有效值：416, 448, 480, 512, 544, 576, 608, 640, 672, 704, 736, 768, 800, 832, 864, 896, 928, 960, 992, 1024
```

**多尺度训练**（高级）：
```python
# 在训练期间动态改变图像大小
# YOLO支持 multi-scale training
# 但需要代码修改

# 优势：模型对不同分辨率更鲁棒
# 缺点：训练更慢，需要更多显存
```

### 6. workers: 4
**功能**：数据加载的并行工作线程数

**原理**：
```
单线程加载数据：                  多线程并行加载数据：
┌──────────────────┐             ┌──────────────────┐
│ 主进程           │             │ 主进程 (GPU训练) │
│ ├─加载图像       │             │                  │
│ ├─处理数据       │    速度慢     │ ┌──────────────┐ │
│ ├─增强           │             │ │ Worker 1     │ │
│ └─GPU训练        │             │ │ ├─加载图像    │ │
│   (等待数据)     │             │ │ └─处理数据    │ │
└──────────────────┘             │ │              │ │
                                  │ │ Worker 2     │ │
                                  │ │ ├─加载图像    │ │ 并行
                                  │ │ └─处理数据    │ │
                                  │ │              │ │
                                  │ │ Worker 3     │ │
                                  │ │ ├─加载图像    │ │
                                  │ │ └─处理数据    │ │
                                  │ └──────────────┘ │
                                  │ (准备好数据)   │ │
                                  └──────────────────┘
```

**CPU核心和workers的关系**：
```
CPU核心 = 16个

最优workers数量：
  ├─ 如果batch=16: 建议workers=4-8
  ├─ 如果batch=32: 建议workers=8-12
  ├─ 如果batch=64: 建议workers=12-16
  └─ 不要超过CPU核心数

workers过多的危害：
  ├─ 过度占用CPU
  ├─ 内存占用增加
  └─ 反而拖累整体速度
```

**调优指南**：
```yaml
# ✅ 当前配置：适合batch=16
workers: 4

# CPU少于8核的机器
workers: 2

# CPU有16核以上
workers: 8

# 特殊情况：数据加载成为瓶颈
workers: 0  # 关闭多进程，使用主线程
           # 用来排查问题

# 问题排查指令
# 在训练开始时观察：
# - GPU利用率 100% → workers充分
# - GPU利用率 < 80% → workers可能需要增加
# - CPU占用 > 90% → workers过多
```

### 7. mosaic: 1.0
**功能**：马赛克数据增强的使用概率

**原理**：马赛克增强是什么？
```
普通图像                     马赛克图像（4张合并）
┌──────────┐                 ┌────────────────┐
│  fish    │                 │ fish │ debris  │
│          │  mosaic=1.0     ├─────┼─────────┤
│  feed    │  ─────────→     │ feed│background│
│          │                 ├─────┼─────────┤
└──────────┘                 │other│ water   │
                             └────────────────┘

优点：
1. 每个batch包含4倍多的对象
2. 增加小目标的学习机会
3. 强制模型学习目标的多种背景
4. 增强模型的泛化能力
```

**数学表示**：
```python
# 4张图像的随机组合
mosaic_image = concatenate([
    image1[0:h//2, 0:w//2],
    image2[0:h//2, w//2:w],
    image3[h//2:h, 0:w//2],
    image4[h//2:h, w//2:w]
])

# mosaic=1.0 的意思是 100%的batch都使用
# mosaic=0.5 的意思是 50%的batch使用，50%不使用
```

**调优指南**：
```yaml
# ✅ 推荐：1.0 (始终使用)
mosaic: 1.0

# 理由：
# - 小目标检测任务特别需要mosaic
# - 可以显著提升recall和mAP
# - 对鱼和饲料检测特别有效

# 特殊情况：
# 如果你的数据集已经有很多目标聚集的图像
mosaic: 0.8  # 减少频率，避免过度增强

# 保守策略
mosaic: 0.5  # 只在一半的batch使用
```

**观察效果**：
```
mosaic=0.0（关闭）
  └─ 模型可能漏检集群目标

mosaic=1.0（始终开启）
  └─ 模型更擅长处理复杂场景 ✅
```

### 8. close_mosaic: 10
**功能**：训练的最后N个epoch关闭mosaic增强

**原理**：
```
训练过程：
Epoch 1-290        Epoch 291-300
┌──────────────┐   ┌───────────┐
│ mosaic = ON  │→  │ mosaic=OFF│
│ 强增强       │   │ 弱增强    │
│ 学习多样化   │   │ 微调精细  │
└──────────────┘   └───────────┘
      ↓                  ↓
学习鲁棒特征        优化精确定位
```

**为什么要关闭？**
```
Mosaic优点：多样化训练
Mosaic缺点：可能破坏自然图像的定位精度

在训练后期：
1. 模型已学习足够的鲁棒特征
2. 需要优化对自然图像的精确定位
3. 关闭mosaic，让模型微调坐标回归
4. 提升mAP和精确度
```

**调优指南**：
```yaml
# ✅ 推荐：close_mosaic: 10 (最后10个epoch)
close_mosaic: 10

# 根据epoch调整
# 如果 epochs: 300
#   最后10个 ≈ 3.3% 训练时间，比例合理
#   close_mosaic: 10 ✅

# 如果 epochs: 500
#   close_mosaic: 15-20  (3-4%)

# 如果 epochs: 100
#   close_mosaic: 5  (5%)

# 没有更好的实证，通常10是默认值
```

**效果评估**：
```
观察指标：
├─ 有close_mosaic
│  └─ 最后10个epoch mAP继续上升 +0.5-1%
│
└─ 没有close_mosaic (设置为0)
   └─ mAP在epoch 290左右可能下降
      (因为高强度增强干扰精细定位)
```

### 9. mixup: 0.2
**功能**：混合增强的使用概率（混合两张图像）

**原理**：
```
原始图像 A        原始图像 B         混合图像 (mixup=0.2)
┌──────────┐    ┌──────────┐       ┌──────────┐
│          │    │          │       │  A 80%   │
│  Fish    │    │  Feed    │  →    │+ B 20%   │
│          │    │          │       │(透明混合)│
└──────────┘    └──────────┘       └──────────┘

公式：
mixed_image = λ × image_A + (1-λ) × image_B
mixed_label = λ × label_A + (1-λ) × label_B

其中 λ 由Beta分布采样，0.2表示使用的概率
```

**效果对比**：
```
mixup=0.0（关闭）              mixup=0.2（打开）
├─ 每张图单独训练              ├─ 图像混合，边界模糊
├─ 模型可能对边界敏感          ├─ 模型学习更平滑的决策
├─ 推理时可能过于"刚性"        ├─ 推理时更鲁棒
└─ mAP可能 baseline           └─ mAP +1-2% ✅
```

**为什么叫mixup？**
```
在图像分类中：
    0.8 × Fish + 0.2 × Feed
    = "有点像Feed的Fish图像"
    模型学会渐进式分类

在目标检测中：
    有时一张图既有Fish又有Feed
    mixup模拟这种自然情况
```

**调优指南**：
```yaml
# ✅ 推荐：mixup: 0.2 (当前配置)
mixup: 0.2

# 根据数据集和任务调整
# 如果你的数据集：
  
  - 类别分布不均
    mixup: 0.3  # 增加到3-0%，帮助平衡
    
  - 大量相似目标
    mixup: 0.4  # 增加到40%，强化分辨能力
    
  - 背景很干净，目标独立
    mixup: 0.1  # 降低到10%，减少不必要的混合
    
  - 实验早期
    mixup: 0.0  # 关闭，让模型先学基础

# 关键：
# 不要太高 (> 0.5)，容易破坏样本
mixup: 0.5  # ❌ 太高，图像混合过度
```

**观察指标**：
```
WandB监控：
├─ 训练loss: 应该更平滑，不会出现尖峰
├─ 验证mAP: 应该更稳定，不会大幅波动
└─ 推理准确率: 应该对噪声和失焦更鲁棒
```

### 10. patience: 50
**功能**：早停（Early Stopping）的耐心值

**原理**：
```
监控验证mAP的变化：

mAP
 │  ╱╲
 │ ╱  ╲  ╱╲╱╲
 │╱    ╲╱    ╲
 └────────────────── Epoch
     50   100   150   200
     
最优点在 Epoch 100
但继续训练到 Epoch 150 (50个epoch无改进)
patience=50 时在 Epoch 150 停止
```

**算法**：
```python
best_mAP = 0
patience_counter = 0

for epoch in range(epochs):
    val_mAP = validate()
    
    if val_mAP > best_mAP:
        best_mAP = val_mAP
        patience_counter = 0  # 重置计数器
        save_best_model()
    else:
        patience_counter += 1  # 增加计数器
        
    if patience_counter >= patience:
        print(f"早停：{patience}个epoch无改进")
        break  # 停止训练
```

**为什么需要早停？**
```
继续训练的风险：
1. 浪费计算资源（没有收益）
2. 容易过拟合（在training set上过度训练）
3. 验证mAP可能开始下降

早停的好处：
1. 节省时间 (50-80%)
2. 选择最优的模型
3. 防止过拟合
```

**调优指南**：
```yaml
# ✅ 推荐：patience: 50 (当前配置)
patience: 50

# 根据数据集和timeout调整：

# 小数据集 (< 1000 images)
patience: 20  # 早停更激进，防止过拟合

# 中等数据集 (1000-10000 images) ← 你的情况
patience: 50  # 平衡选择 ✅
```

### 11. seed: 42
**功能**：随机数种子，确保可重复性

**原理**：
```
深度学习中有很多随机过程：
├─ 数据打乱顺序
├─ 初始权重随机初始化
├─ Dropout随机关闭神经元
├─ 数据增强的随机变换
└─ 小批量梯度下降的随机采样

设置 seed=42：
└─ 所有随机过程都可重现
   └─ 使用相同seed运行两次 → 完全相同结果
```

**为什么叫42？**
```
这是一个梗 😄

来自《银河系漫游指南》：
"终极问题的答案是 42"

在机器学习中：42被约定俗成地用作"默认种子"
(你可以用任何其他数字)
```

**调优指南**：
```yaml
# ✅ 推荐：seed: 42 (标准做法)
seed: 42

# 实验对比：为了公平比较两个配置

# 配置A (baseline)
seed: 42
# → 训练run_1, run_2, run_3
# → 得到三个完全相同的mAP值（取平均）

# 配置B (新的hyper-parameters)
seed: 42
# → 训练run_1, run_2, run_3
# → 得到三个完全相同的mAP值（取平均）

# 对比 config_A vs config_B
# 差异确实来自配置，而不是随机性

# 其他场景：
seed: 0      # 任何数字都可以
seed: 2024   # 也常见
seed: 123    # 也可以
```

**多次运行的原因**：
```
即使设置了seed，由于：
├─ GPU浮点计算的不确定性
├─ 并行处理顺序不同
└─ 某些操作的随机性难以完全控制

所以通常需要运行3-5次取平均
```

## 常见问题排查

### 问题1：GPU显存不足
```yaml
# 症状：CUDA out of memory

# 解决方案（按优先级）：
1. batch: 16 → 8        # 立即有效，可降低到batch=4
2. imgsz: 832 → 640     # 显存减少30%
3. workers: 4 → 2       # 小幅帮助
4. 关闭某些特性
   mosaic: 1.0 → 0.5    # 可能有效，但不推荐
```

### 问题2：训练很慢（GPU使用率低）
```yaml
# 症状：
# - GPU占用 < 50%
# - 训练1个epoch需要10分钟

# 原因和解决方案：
1. workers太少
   workers: 4 → 8        # 增加数据加载并行度

2. 硬盘IO慢
   workers: 4 → 0        # 改用单进程测试
   
3. batch太小
   batch: 8 → 16         # 增加GPU工作量

4. 数据增强太重
   mosaic: 1.0 → 0.8     # 降低增强频率
```

### 问题3：mAP不上升，loss卡住
```yaml
# 症状：
# - 训练loss停留在某个值
# - 验证mAP不变或下降

# 原因：学习率太高或太低
解决方案：
  - 检查学习率 (默认 lr0=0.01)
  - 在trainer.py修改: lr0=0.001 (降低10倍)
  - 重新训练
```

### 问题4：模型过拟合
```yaml
# 症状：
# - 训练mAP 0.95，验证mAP 0.65

# 解决方案：
1. 增加正则化
   weight_decay: 0.0005  # 在trainer.py中
   
2. 降低增强强度（不推荐）
   mosaic: 0.5
   mixup: 0.1
   
3. 更多数据（收集更多图像）

4. 增加epoch让验证mAP恢复
   patience: 50 → 100    # 给更多机会
```
